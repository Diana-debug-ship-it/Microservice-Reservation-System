# Распределенная система бронирования отелей (микросервисы)

Проект представляет собой событийно-ориентированную (Event-Driven) микросервисную систему автоматизации бронирования номеров, обработки платежей и отправки уведомлений. 

Система спроектирована с учетом требований к высокой автономности сервисов, аудируемости финансовых транзакций и защиты от овербукинга.

## Технологический стек

* **Язык разработки:** Java 21 (использование Sealed-интерфейсов, Pattern Matching)
* **Платформа:** Spring Boot 3.x, Spring Data JPA, Spring Web
* **Брокер сообщений:** Apache Kafka (асинхронное межсервисное взаимодействие)
* **Кэширование и распределенный таймер:** Redis (механизм Keyspace Notifications)
* **Базы данных:** PostgreSQL (отдельная изолированная база данных для каждого микросервиса)
* **Инструменты:** Docker Compose, Maven, MapStruct, Lombok

## Архитектура и структура модулей

Проект реализован в рамках единого монорепозитория и разделен на изолированные доменные модули:

* `booking-service` — управление номерным фондом, отелями, валидация дат и оркестрация процесса оплаты.
* `payment-service` — симулятор банковского платежного шлюза (эквайринга) с поддержкой различных стратегий оплаты.
* `notification-service` — асинхронный аудит и отправка уведомлений клиентам по различным каналам.
* `shared` — общий модуль, содержащий неизменяемые контракты (DTO), sealed-интерфейсы и перечисления (Enums).

## Ключевые архитектурные решения

### 1. Гибридное межсервисное взаимодействие (HTTP + Kafka)
В системе разделены критические синхронные процессы и второстепенные асинхронные задачи:
* Взаимодействие между `booking-service` и `payment-service` происходит синхронно по HTTP (через Spring HTTP Interfaces). Это гарантирует моментальный ответ от банковского шлюза перед изменением статуса брони в системе.
* Отправка уведомлений вынесена в асинхронную шину данных Apache Kafka. Сервис бронирования публикует событие `BookingConfirmedEvent` в топик и сразу возвращает ответ клиенту, не дожидаясь физической доставки уведомления.

### 2. Защита от овербукинга и распределенный таймер в Redis
Для исключения гонки данных и блокировки номеров реализован двухэтапный механизм:
* На уровне базы данных PostgreSQL написан атомарный SQL-запрос, проверяющий пересечение дат для конкретной комнаты перед созданием временной брони.
* При создании бронирования ему присваивается статус `PENDING_PAYMENT`, а в Redis отправляется ключ-таймер с TTL 15 минут. 
* Если пользователь успешно оплачивает бронь, ключ удаляется. Если 15 минут истекают, Redis генерирует событие удаления (`Keyspace Notification`). Инфраструктурный слушатель `BookingKeyExpirationListener` перехватывает сигнал, находит бронь по ID в PostgreSQL и переводит ее в статус `CANCELLED`, освобождая даты для других пользователей. База данных PostgreSQL не нагружается постоянными фоновыми опросами (Polling).

### 3. Полиморфизм в REST API и Pattern Matching
Для поддержки различных методов оплаты (`CARD`, `SBP`) на уровне транспортного слоя используется полиморфный sealed-интерфейс `PaymentDetailsDto`. Аннотации Jackson (`@JsonTypeInfo` и `@JsonSubTypes`) обеспечивают корректную десериализацию абстрактных структур данных из JSON при передаче между микросервисами по сети.
В `payment-service` обработка платежных стратегий реализована через синтаксис `switch-pattern matching` (Java 21).

### 4. Целенаправленная денормализация данных
В момент создания бронирования текстовое название отеля и номер комнаты копируются из сервиса отелей напрямую в таблицу `booking` (создается Snapshot данных на момент покупки). Это обеспечивает:
* Историческую достоверность чека (если отель переименуют через год, в старой брони пользователя останется корректное название).
* Высокую производительность при чтении списка броней пользователем (исключаются сложные `JOIN` запросы между таблицами доменов комнат и отелей).
* Полную автономию `booking-service`, подготавливая его к физическому разделению баз данных на разные физические сервера.

### 5. Аудируемость и паттерн «Гарантированная доставка»
В `notification-service` реализован журнал логирования сообщений. При получении события из Kafka сервис сначала фиксирует намерение в локальной `notification_db` со статусом `CREATED`. Только после этого вызывается стратегия отправки (лог, внешнее API Telegram-бота). 
При успешном исходе статус меняется на `SENT`, при ошибке шлюза — на `FAILED`. Это исключает потерю следов уведомлений при падении внешних сетей и подготавливает систему к реализации механизма повторных попыток (Retry Job).

### 6. Безопасность и управление секретами
В проекте реализовано полное сокрытие чувствительных данных (пароли к базам данных, токен Telegram-бота). В конфигурационных файлах `application.yml` прописаны плейсхолдеры для переменных окружения Spring (`${TELEGRAM_BOT_TOKEN:}`). Реальные секреты передаются локально через параметры запуска среды разработки (Environment variables) или изолированный файл `.env` для Docker, добавленный в `.gitignore`.

## Инструкция по локальному запуску

### 1. Подготовка инфраструктуры
Для запуска баз данных PostgreSQL, брокера сообщений Kafka и кэша Redis в корне проекта настроен Docker Compose. Выполните команду:

```bash
docker compose up -d
```

### 2. Переменные окружения
Для успешного запуска `notification-service` необходимо передать в параметры конфигурации запуска (Run/Debug Configurations -> Environment variables) следующие ключи:
* `TELEGRAM_BOT_TOKEN` — официальный токен вашего бота, полученный от @BotFather.
* `TELEGRAM_TEST_CHAT_ID` — ваш личный ID чата для проверки доставки push-уведомлений.

### 3. Сборка и запуск приложений
Выполните полную сборку проекта из корневой директории через Maven:

```bash
mvn clean install
```

Последовательно запустите главные классы приложений:
1. `BookingServiceApplication` (работает на порту 8080)
2. `PaymentServiceApplication` (работает на порту 8081)
3. `NotificationServiceApplication` (работает в фоновом режиме long-polling)
